# 01 设计文档：需求、选型与 RAG 存储

> 范围：项目需求、技术选型、模型分工、从中文维基到本地知识文件的流程。  
> 问答页 UI、对话实现、提示词细节见后续文档。

---

## 1. 文档目的

作为实现 ingest / 存储 / 同步的依据。

---

## 2. 项目需求

### 2.1 目标

做一个面向玩家的 **星露谷中文 Wiki RAG 问答站**：

- 知识来源：[星露谷中文维基](https://zh.stardewvalleywiki.com/)（MediaWiki）
- 采集入口：`https://zh.stardewvalleywiki.com/mediawiki/api.php`
- 用户用自然语言提问（礼物、作物、任务等），系统根据检索到的维基切片作答，并给出原文链接

2026-09-01 实测站点规模：约 **1996** 篇正式条目、**3265** 个页面（含讨论/模板等）、MediaWiki **1.35.1**。语料小，整库向量可放本机文件。

### 2.2 产品范围（本阶段）

要做：从维基拉正文、清洗、切片；调用百炼 embedding 并写入本地知识文件；管理端「同步 Wiki」按钮（全量或差量）；Docker 部署在自有服务器。

后补：问答界面与流式对话；定时自动同步。

### 2.3 约束

- **版权**：维基内容多为 CC BY-NC-SA 一类协议。切片必须保留页面 URL；公开站注意非商用与署名。
- **礼貌采集**：通过 MediaWiki API 拉取，明确 `User-Agent`，请求间隔约 1～2 秒。
- **费用**：百炼按量计费，用于 embedding 以及后续问答模型。切片、存文件、本地检索在本地完成。
- **部署**：Docker，单机，数据挂 volume。

### 2.4 成功标准（存储阶段）

1. 一次同步后，磁盘上有完整、可对齐的知识快照（见 §6）。
2. 再次同步时，只对 `revid` 变化的页面重新切片和 embedding。
3. 写入采用「先写 `.new` 再 rename」，失败时上一份快照仍可用。
4. 从快照能按问题向量做相似度检索（可用脚本或单测验证）。

## 3. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 应用框架 | **Next.js（App Router）+ TypeScript** | 站点与 ingest 同一语言。本阶段先做同步 API 与脚本，问答页后补。 |
| 运行时 | Node.js，Docker 单容器 | |
| 维基采集 | MediaWiki Action API | `allpages` + `info` / `extracts` / `parse` |
| 切片 | **自研** | 按 H2/H3 切，infobox 单独成块 |
| 向量化 | 百炼 `text-embedding-v4` | HTTP 调用，国内节点 `dashscope.aliyuncs.com` |
| 向量存储 | **本地文件** | `chunks.jsonl` + `embeddings.bin` + `pages.json` |
| 关键词（可选，存储阶段可后做） | MiniSearch 等进程内索引 | 物品名、NPC 名靠字面匹配 |
| 重排序 | 百炼 `qwen3-rerank` | 问答链路，本阶段接口预留，实现放后续文档 |
| 查询改写 | 百炼 `qwen-plus` | 问答阶段：检索前把口语扩成检索词 |
| 回答生成 | 百炼 `qwen-plus` | 问答阶段：根据切片写答案 |
| 测试 | Vitest | 用例放 `lib/**/*.test.ts`；维基正文用本地 fixture |

wikitext 模板若无法用 TypeScript 干净解析，允许增加单独的解析脚本，默认仍以 TS 为准。

### 3.1 仓库与部署（存储相关）

建议目录（实现时可微调）：

```text
scripts/ingest.ts          # 也可由 Next.js 路由复用同一套 lib
lib/wiki.ts                # MediaWiki 客户端
lib/chunk.ts               # 清洗与切片
lib/embed.ts               # 调用 text-embedding-v4

tests/fixtures/wiki/       # 录制的 extracts / parse 原文
app/admin/                 # 同步按钮页（极简）
app/api/admin/sync/        # 触发同步、查询状态

```

Docker：一个 web 容器 + `./data:/app/data`。同步在进程内跑；接口立即返回任务状态，由后台完成 embedding。

## 4. 模型清单

全部通过阿里云百炼（DashScope）。中国内地兼容接口基址：

`https://dashscope.aliyuncs.com/compatible-mode/v1`

（rerank 以百炼文档当时的实际路径为准。）

| 角色 | 模型 ID | 本阶段是否实现 | 何时调用 |
|---|---|---|---|
| 向量化 | `text-embedding-v4`（1024 维） | **要** | 同步时对切片；问答时对用户问题 |
| 重排序 | `qwen3-rerank` | 否（后续） | 问答：粗召回后再打分 |
| 查询改写 | `qwen-plus` | 否（后续） | 问答：检索前把口语扩成检索词 |
| 回答生成 | `qwen-plus` | 否（后续） | 问答：根据切片写答案 |

### 4.1 费用量级（embedding）

内地标价约 **0.5 元 / 百万 token**（Batch 约半价）。按约 2000 篇粗估：

- 第一次全量：大约 **1～4 元**
- 周更差量（普通一周几十页）：大约 **几分钱**
- 大版本周（数百页）：大约 **0.2～1 元**

精确数字取决于切片后的实际 token，以第一次同步账单为准。新账号免费额度通常不够覆盖全库。

问答阶段的 plus / rerank / 问题 embedding 费用见后续文档。

## 5. RAG 流程（到存储为止）

知识在磁盘落稳之前，不经过问答模型。

```text
星露谷中文维基 API
        │
        ▼
  管理端「同步 Wiki」按钮
        │
        ▼
  已有 pages.json？ ──否──► 全量：扫描 ns=0 全部条目
        │是
        ▼
  对比每页 revid → 只要：修改 / 新增 / 删除（含改成重定向）
        │
        ▼
  拉正文（优先 extracts 纯文本，否则 parse 后剥 HTML）
        │
        ▼
  清洗：去掉皮肤 CSS、目录噪音；infobox 写成可读短句
        │
        ▼
  切片：按 H2/H3；infobox 独立成块；每块带 title / url / section / pageid / revid
        │
        ▼
  text-embedding-v4（仅新切片；未改动页沿用已有向量）
        │
        ▼
  与未变更的旧切片在内存合并
        │
        ▼
  原子写入：chunks.jsonl + embeddings.bin + pages.json
```

问答阶段只读上述文件：问题向量化 → 与 `embeddings.bin` 比相似度 → rerank → plus 作答。

### 5.1 采集规则

- **知识范围**：主空间 `ns=0`。分类页仅作 metadata（v1 可后做）。
- **重定向**：收录目标正规条目。
- **正文**：优先 `prop=extracts&explaintext=1`；扩展不可用则 `action=parse` 后去标签。送 embedding 的是清洗后的纯文本。
- **切片**：一页多块。旧页更新时按 **pageid 整组替换**。
- **标识**：`chunk.id = "{pageid}#{sectionIndex}"` 或等价稳定规则；同一 pageid 重切后旧 id 全部作废。

### 5.2 页面结构

数据源是星露谷中文维基，结构以 infobox、日程、送礼、任务列表为主。清洗和切块按该结构处理。

## 6. 存储设计

### 6.1 文件快照

- 体量：约 2 万条切片量级 × 1024 维 float32 ≈ **80MB** 向量，加正文通常仍远小于 1GB。
- 更新：周级、单写者，每次产出一份完整快照。
- 运维：备份 = 拷 `data/`；排错可直接打开 jsonl。
- 部署：Docker volume。

### 6.2 目录

```text
data/
  chunks.jsonl         # 一行一条切片（UTF-8）
  embeddings.bin       # Float32 little-endian，行优先，每行 1024 维
  pages.json           # pageid → title, revid
  meta.json            # 模型、维度、条数、同步时间
  sync.lock            # 同步互斥（存在即视为进行中或崩溃残留）
  sync-status.json     # 供按钮轮询：idle / running / success / error
```

`data/` 加入 `.gitignore`。镜像内不打包知识文件。

### 6.3 `chunks.jsonl`

每行一个 JSON 对象，字段 v1 固定如下：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 切片稳定 id |
| `pageid` | number | MediaWiki 页面 id |
| `title` | string | 页面标题 |
| `url` | string | 规范中文维基 URL |
| `section` | string | 章节名；infobox 用 `"__infobox__"` |
| `text` | string | 清洗后的纯文本 |
| `revid` | number | 该页本次同步时的修订号 |
| `order` | number | 页内顺序，从 0 起，与 embedding 行顺序一致 |

向量写入 `embeddings.bin`。`chunks.jsonl` 第 *i* 行 ↔ `embeddings.bin` 第 *i* 条向量，必须严格对齐。`meta.json.count` 等于行数。

### 6.4 `embeddings.bin`

- 类型：IEEE-754 float32，小端
- 布局：`count * 1024` 个连续 float
- 维度：1024，与 `text-embedding-v4` 调用参数一致
- 校验：`fileSize === count * 1024 * 4`

### 6.5 `pages.json`

```json
{
  "syncedAt": "2026-09-01T16:00:00.000Z",
  "pages": {
    "164": { "title": "阿比盖尔", "revid": 89231 }
  }
}
```

用于差量判定。

### 6.6 `meta.json`

```json
{
  "embeddingModel": "text-embedding-v4",
  "dimensions": 1024,
  "count": 0,
  "wiki": "https://zh.stardewvalleywiki.com",
  "syncedAt": null,
  "lastSync": {
    "mode": "full",
    "pagesChanged": 0,
    "chunksEmbedded": 0,
    "ok": true,
    "error": null
  }
}
```

### 6.7 原子写入

1. 在内存得到完整新快照（差量 = 旧切片去掉变更 pageid + 新切片）。
2. 写入 `chunks.jsonl.new`、`embeddings.bin.new`、`pages.json.new`、`meta.json.new`。
3. `fsync` 后按固定顺序 `rename` 成正式文件。
4. 删除 `.new` 残留与 `sync.lock`。

进程崩溃时：正式文件仍是上一份完整快照；下次同步视为未完成，可重跑。

### 6.8 进程内使用方式（为后续问答预留）

Web 进程启动或检测到 `meta.json` 的 mtime 变化后，将 `embeddings.bin` 读入 `Float32Array`，将 `chunks.jsonl` 读入内存数组。检索为余弦 / 点积。

同步成功后触发一次索引 reload。

## 7. 差量更新

### 7.1 判定

以 MediaWiki `lastrevid` 为准。每次同步拉取当前 `ns=0` 全部 `pageid / title / lastrevid`（以及是否 redirect），与 `pages.json` 比对。约 2000 条，只打 Wiki API。

| 情况 | 处理 |
|---|---|
| revid 相同 | 保留该 pageid 下全部旧切片与向量 |
| revid 变化 | 删除该 pageid 旧切片，整页重拉、重切、重 embedding |
| 线上有、本地无 | 当新页 ingest |
| 本地有、线上无，或变成 redirect | 删除该 pageid 全部切片 |

没有 `pages.json` 或 `count === 0`：视为全量。

### 7.2 触发方式

- 管理页 `/admin` 提供「同步 Wiki」按钮。
- 鉴权：环境变量 `ADMIN_TOKEN`。
- `POST` 开始同步并立即返回；`GET` 读 `sync-status.json`。
- 互斥：`sync.lock`，进行中拒绝第二次点击。超时或崩溃后可清锁或启动时检测陈旧锁。
- 同一套 `lib/sync.ts`：无本地快照则全量，有则差量。

运营按周在管理页触发。定时自动同步为后补，复用同一 sync 函数。

### 7.3 同步状态（按钮轮询）

`sync-status.json` 字段：`status`、`mode`（`full` | `incremental`）、`startedAt`、`finishedAt`、`pagesChanged`、`chunksEmbedded`、`message`。

## 9. 风险（存储阶段）

| 风险 | 对策 |
|---|---|
| infobox/表格清洗不够，切片不可用 | 先用核心页 fixture 把切片测试写绿，再全量同步 |
| extracts 扩展不可用 | 回退 parse + 去 HTML |
| 维基限流 | 间隔 + 重试；原始 JSON 可缓存在 `data/raw/`（可选，不进向量） |
| 中文站相对英文站滞后 | `revid` / `syncedAt` 保留；问答阶段再提示数据来源日期 |
| 同步中途失败 | 原子替换；正式文件始终完整 |

## 11. 测试（TDD）

实现采用测试驱动：先写失败用例，再写实现直到通过，最后重构。

### 11.1 范围

- 切片、文件对齐、原子写入、revid 差量：每个行为先补测试。
- 维基 API、百炼 embedding：实现为可注入依赖；测试里使用本地 fixture 和固定假向量（如指定长度的 `Float32Array`）。
- 同步接口：测任务状态（开始 / 进行中 / 成功 / 失败）与锁。

### 11.2 约定

- 框架：Vitest。
- Fixture：至少包含 NPC、作物、社区中心各一篇的 `extracts` / `parse` 原文；切片期望用黄金文件（小份 jsonl），规则变更时同步更新该文件。
- embedding 客户端契约：`dimensions === 1024`，单次最多 10 条。差量测试断言：revid 未变时假 embedding 调用次数为 0。
- 一次测试只覆盖一个行为（例如先独立 infobox，再切 H3）。

### 11.3 顺序

1. 落下 fixture。
2. 切片测试变绿（含 infobox、`section`、无皮肤噪音）。
3. store 测试变绿（行与向量对齐；写入失败时正式文件仍为上一份快照）。
4. sync 测试变绿（改 / 增 / 删 / 重定向）。
5. 接入真实 API，用少量页面做一次人工确认。
